# @nabvy/db

Drizzle schema (one file per module), migrations, the migration runner, `withUser`, the database
roles, the generated Better Auth schema and seeds (`docs/engineering.md`, "Database access"). This
is the shared core (task 0.2–0.3 foundation). Each atomic module adds its own tables in its own
schema file and migrations folder (`docs/decisions.md`, "Atomic modules").

## Layout

```
src/
  index.ts                 createDb, getDb, withUser, withPipeline, moduleSchema, idColumn, timestampColumns
  schema/<module>.ts       a module's tables, imported as '@nabvy/db/schema/<module>'
  schema/better-auth.ts    generated by `pnpm auth:generate`; never edited by hand
migrations/
  core/                    hand-written SQL: extensions, roles, uuidv7(), RLS helpers, view checks
  <module>/
    module.json            { module, schema, dependsOn }
    drizzle.config.ts      this module's Drizzle Kit config: its schema file, its folder
    meta/                  this module's Drizzle journal and snapshots (Drizzle Kit's, not edited)
    <YYYYMMDDHHMMSS>_<slug>.sql
scripts/
  migrate.mjs              the runner: plan | apply | emit
  generate.mjs             pnpm db:generate <module> [--custom] [--name <slug>]
  generate-better-auth.mjs pnpm auth:generate
  seed.ts                  pnpm db:seed (founder users)
tests/*.test.sql           SQL tests run by pnpm db:dry-run
test/*.test.ts             Vitest: runner, conventions, scaffold, withUser against Postgres
better-auth/auth.config.ts the plugin list the Better Auth CLI generates from
```

## One Postgres schema per module

A module's tables live in a Postgres schema named after it in snake case (`listing-registry` →
`listing_registry`). The schema is the ownership boundary:

- **The owning module writes.** Only `services/<module>` imports the tables from
  `@nabvy/db/schema/<module>`. No table sits in `public`.
- **Others read only `v_` views.** Views are exported with a `v` prefix (`vListings` for
  `listing_registry.v_listings`). A test fails if a service imports, or re-exports, anything
  else from another module's schema file, by package path or relative path; namespace imports
  (`import * as`) of another module's schema are refused.
- **Reserved names:** Supabase's schemas (`auth`, `storage`, `extensions` and the rest),
  `nabvy_core`, `apify_gateway`, `marketplace_monitor` (deprecated; left alone). The Better Auth
  tables are in `better_auth` because `auth` belongs to Supabase.

A schema file:

```ts
import { index, integer, text, uuid } from 'drizzle-orm/pg-core'
import { idColumn, moduleSchema, timestampColumns } from '../module-schema'

export const schema = moduleSchema('hunt-manager')

export const hunts = schema.table('hunts', {
  id: idColumn(),                          // uuid default nabvy_core.uuidv7()
  userId: uuid('user_id').notNull(),
  radiusKm: integer('radius_km').notNull(),
  ...timestampColumns(),                   // created_at, updated_at (timestamptz)
}, (t) => [index('hunts_user_id_idx').on(t.userId)])

// A view other modules may read: declared here, created by hand-written SQL (below).
export const vHunts = schema.view('v_hunts', { id: uuid('id'), radiusKm: integer('radius_km') }).existing()
```

Use explicit snake_case column names, `timestamp(..., { withTimezone: true })`, and money as
two columns (`price_minor bigint`, `currency text check (currency in ('GBP','EUR'))`), never a float.

## Migrations

**Choice: one Drizzle Kit config and journal per module, timestamp-named SQL files, and a runner
that orders modules by declared dependencies.** Why:

- Drizzle Kit's journal (`meta/_journal.json`) is a single file that every `generate` rewrites.
  One journal for the whole database would make every parallel module branch conflict. One per
  module (`migrations/<module>/meta/`) means a branch touches only its own folder.
- File names are `<14-digit UTC timestamp>_<slug>.sql` (Drizzle Kit's `supabase` prefix), so
  two branches never pick the same name, and the names match `supabase/migrations`.
- The order across modules does **not** depend on timestamps. A branch that merges later can
  carry an earlier timestamp, so the runner sorts modules by the `dependsOn` lists in their
  `module.json` (core first, ties by name), then files by name inside a module. A module that
  reads another's views lists it in `dependsOn`.
- A ledger, `nabvy_core.schema_migrations (module, name, checksum)`, records what is applied.
  Each file runs in one transaction with its ledger row. A file whose checksum differs from the
  ledger stops the run. Migrations are forward-only: never edit a merged file, add a new one.

### Adding tables to a module

1. Edit `src/schema/<module>.ts`.
2. `pnpm db:generate <module>` writes `migrations/<module>/<timestamp>_<slug>.sql` (add
   `--name <slug>`).
3. Hand-written SQL (grants, RLS, views, triggers, partitions, pg_cron) goes in its own file:
   `pnpm db:generate <module> --custom --name <module>_access` creates an empty timestamped file
   in the journal; fill it using the template below.
4. `pnpm db:dry-run` (below) and commit the SQL, `meta/` and the schema file together.

Template for the access file of a module with user rows:

```sql
-- Who may use the schema. Never grant anon or authenticated (Supabase's Data API roles).
grant usage on schema hunt_manager to nabvy_app, nabvy_pipeline;

-- Owner's writes. The web app writes user rows; pipeline tasks write pipeline tables.
grant select, insert, update, delete on hunt_manager.hunts to nabvy_app;
select nabvy_core.enable_user_rls('hunt_manager.hunts');         -- user_id = withUser's user
select nabvy_core.allow_pipeline('hunt_manager.hunts', 'select'); -- pipeline reads every hunt
grant select on hunt_manager.hunts to nabvy_pipeline;
select nabvy_core.track_updated_at('hunt_manager.hunts');

-- The read interface for other modules: security_invoker so RLS applies to the caller, and an
-- explicit allowlist of columns (never select *; never seller identity or the raw provider row).
create view hunt_manager.v_hunts with (security_invoker = true) as
  select id, radius_km from hunt_manager.hunts;
grant select on hunt_manager.v_hunts to nabvy_app, nabvy_pipeline;
```

Every table carrying a `user_id` gets `enable_user_rls`. The policy compares the column with
`nabvy_core.current_user_id()`, which reads `app.user_id`. Pipeline tables use `allow_pipeline(table,
'select' | 'insert' | 'update' | 'delete' | 'all')` together with matching grants. RLS denies by
default, so a role with a grant but no policy sees nothing.

### Running

```
pnpm db:plan      # every migration in apply order, with checksums
pnpm db:migrate   # apply pending ones with psql (standard PG* variables, as the migration role)
pnpm db:dry-run   # throwaway local Postgres: supabase/migrations, then this runner, then all tests
node packages/db/scripts/migrate.mjs emit <module>/<file>   # lock, guard, SQL, ledger row
```

The dry-run applies, in the order the live project gets them: Supabase stand-ins, then
`supabase/migrations` (the Apify gateway), then this runner (twice, to prove the second run is a
no-op), then `supabase/tests/*.test.sql` and `tests/*.test.sql`. The coordinator applies merged
migrations to Supabase: run `plan`, compare it with `select module, name from
nabvy_core.schema_migrations`, and apply each pending file's `emit` output in plan order.

Each file runs in one transaction that first takes a shared advisory lock
(`pg_advisory_xact_lock`) and then stops if the file is already in the ledger, so two runners
never apply the same file twice. `emit` prints the same lock and guard but no `begin`/`commit`:
the connector's `apply_migration` already wraps its input in one transaction. With psql, run
the output with `-1`.

After applying to the live project, the coordinator runs the checks the dry-run cannot make
faithfully, because its `anon`/`authenticated` stand-ins carry none of Supabase's grants:
`select * from nabvy_core.view_violations()` (expect no rows);
`select rolname, rolbypassrls from pg_roles where rolname like 'nabvy%'` (expect `false`); and
`has_schema_privilege('anon' | 'authenticated', <module schema>, 'usage')` (expect `false`).

New functions in `nabvy_core` must `revoke all on function … from public` in their migration.
Postgres's global default grants EXECUTE to PUBLIC, and a per-schema default cannot remove it,
so the dry-run fails when any `nabvy_core` function other than `uuidv7()` and
`current_user_id()` is executable by an application role.

## Roles, `withUser` and RLS

- `nabvy_app` (web app) and `nabvy_pipeline` (pipeline tasks), both `NOBYPASSRLS`, created
  `NOLOGIN` by the core migration. The coordinator enables login and sets passwords on the live
  project out of band; no credential is in a migration. Their search path is Supabase's default
  (`"$user", public, extensions`), so vector and trigram operators resolve.
- `getDb('app')` / `getDb('pipeline')` open pools from `DATABASE_URL` / `DATABASE_URL_PIPELINE`
  (`@nabvy/config`). Supabase's pooler runs in transaction mode, so nothing relies on session state.
- `withUser(userId, fn)` opens a transaction, sets `app.user_id` with `set_config(…, true)` (the
  parameterised `SET LOCAL`), runs `fn(tx)` and commits. Outside it, user tables return nothing.
- `withPipeline(fn)` is a plain transaction on the pipeline pool.
- Repo functions take a `Queryable` (a `Db` or a `Tx`), so the same function runs inside
  `withUser` from a procedure or inside `withPipeline` from a task.

Tested in `tests/core.test.sql` (on probe tables built with the helpers: outside `withUser`
nothing; inside, only the user's rows; no writes for another user; the pipeline reads hunts and
inserts alerts but cannot read profiles or its own alerts back) and in
`test/with-user.integration.test.ts` (the TypeScript helper against Postgres, including no leak
to the next transaction on a pooled connection).

## Views

`v_` views are the only way other modules and users read a module's data. Two rules, checked by
`nabvy_core.view_violations()` over every view and materialised view in a module schema (the
schemas the migration ledger knows), in the dry-run and on the live project:

1. **`security_invoker = true`** on every plain view in a module schema, whatever its name, so
   RLS applies to the reader. A plain view runs as its owner and would bypass RLS as soon as it
   is granted to an application role.
2. **An allowlist of columns that never includes seller identity**, on every `v_` view, every
   `mv_` materialised view, and any other view `nabvy_app` can select. No column named like
   `seller…`, `profile_url`/`profile_link`/`profile_pic…`, `raw`, `raw_…`, `…_raw` or
   `source_fields`. Actor data is kept in full in the owning module's tables, and developers see
   it there; end users never see seller identity (`docs/decisions.md`, "Actor data kept in full").
   The name check is a backstop: it does not replace choosing an allowlist.

Materialised views (`mv_`) run as their owner and have no RLS. They carry aggregates only, and
never user or seller rows. An internal view that shows developers seller data is allowed only
if it is not named `v_`/`mv_` and is not granted to `nabvy_app`.

## Every table

`id uuid default nabvy_core.uuidv7()` (`idColumn()`), `created_at`/`updated_at` (`timestampColumns()`)
with `nabvy_core.track_updated_at(table)` in the access file. Soft delete only where the spec says
so. Extensions are in the `extensions` schema: `pg_trgm`, `vector` (pgvector) and `postgis`. CI
installs pgvector and PostGIS into its Postgres 17 container, the version the live project runs.

## Better Auth

`pnpm auth:generate` runs the Better Auth CLI (`auth generate`) against `better-auth/auth.config.ts`
(magic link, Google, admin, Turnstile captcha, Stripe; `docs/decisions.md`), then moves the tables
into the `better_auth` schema. That move is the only change and it is scripted, so the file is
never edited by hand. Then `pnpm db:generate better-auth`. IDs are UUIDs generated by the database
(`gen_random_uuid()`, Better Auth's `generateId: 'uuid'`).

Better Auth reads sessions before a user is known, so its tables cannot sit behind `withUser`.
The running instance connects as its own role, `nabvy_auth` (`DATABASE_URL_AUTH`), which can use
`better_auth.user`, `session`, `account` and `verification` and nothing else; `nabvy_app` and
`nabvy_pipeline` cannot read them and may only call `better_auth.account_active(user_id)`, which
answers whether an account may be acted for (task 4.0, `services/auth/README.md`).

## Seeds

- **Founder users:** `pnpm db:seed` reads `ADMIN_EMAILS` (config group `auth`) and calls
  `better_auth.seed_founders(emails)`, which creates each address as an `admin` user or promotes
  it. It is idempotent. It runs with psql as the migration role. The `audit_log` row from
  `docs/engineering.md` arrives with the ops-monitor module.
- **No H3 cells seed.** The build pack's UK H3 resolution-4 `cells` seed is superseded: search
  planning uses verified city-page centres (`city-pages.seed.json`), per region and never per
  user (`docs/decisions.md`, Precedence, "Search planning"). The crawl-planner module seeds those.

## Decisions

- One schema per module; `v_` views as the only cross-module read path; ownership checked by
  tests (`test/conventions.test.ts`) and view rules by SQL (`view_violations()`).
- Per-module Drizzle configs and journals plus a dependency-ordered runner with a checksum ledger
  (above), instead of one shared journal or Drizzle's migrator. The runner uses psql, like the
  existing dry-run, and the coordinator can replay its output through the Supabase connector.
- `nabvy_core.uuidv7()` is schema-qualified, so Postgres 18's built-in `uuidv7()` never clashes.
- `supabase/migrations` stays for the Supabase-platform pieces (the Apify gateway) and runs first.
- PostgREST: no Nabvy table is in `public`, and `anon`/`authenticated` reach no module schema
  (checked in the dry-run). Turning off the Data API for `public` is a dashboard setting on the
  live project, for the coordinator.
