# Open questions: inventory

- **2026-09-25, w2 inventory: a `currency` column the card does not list.** The card's "Owns" line names `cost_minor` and `sold_minor` but no currency, while the shared money contract is never a bare number (`packages/contracts/src/core/money.ts`: GBP and EUR are kept apart, never converted). Option taken: one `currency` column per item, set at purchase, and a sale in another currency is refused (`inventory.currency_mismatch`) rather than converted. Conservative because it adds no exchange rate (CLAUDE.md, "No invented numbers") and no user-facing wording.
- **2026-09-25, w2 inventory: where an item sold (`sold_on`).** The card names `sold_on` without values. Option taken: the shared `Source` enum (`ebay`, `facebook`, `gumtree`, `vinted`, `cex`), optional, so a user who sold in person or elsewhere leaves it blank. Adding a value such as "other" or "in person" is user-facing wording, so it is left to the owner. Conservative because it reuses an existing enum and invents no wording.
- **2026-09-25, w2 inventory: no remove or edit of a purchase.** The card lists adding a purchase and capturing a sale; it does not list deleting an item or correcting its cost, product or purchase date. Option taken: `nabvy_app` may insert and may update only the four sale columns (a sale can be corrected); it has no delete grant. A user who entered a purchase wrongly cannot yet remove it. Conservative because it is the smallest grant; the owner decides whether the inventory page needs "remove item" and "edit purchase", which would be a follow-up with their own probes in `packages/db/tests/inventory.test.sql`.
- **2026-09-25, w2 inventory: a suppressed listing's link.** Rule 5 says a view that shows listings leaves out suppressed ones; `app.v_inventory_items` shows the user's own items, which may name a listing by ID. Option taken: the item stays (it is the user's money record), but `source_listing_id` reads null while the listing is suppressed or `listing-suppression` is off, so the app can never join a suppressed listing back onto a card. Conservative because it never drops a user's own purchase and fails closed on the link.
- **2026-09-25, w2 inventory: `nabvy_core.view_violations()` still does not scan `app.*` views.** As `docs/questions/listing-card.md` recorded, the check's schema list comes from the migration ledger, so the second `app.*` view (`app.v_inventory_items`) is also outside it. Option taken: `packages/db/tests/inventory.test.sql` asserts `security_invoker`, the exact column list and the absence of seller-like or user columns by hand, as listing-card's test does. Still needs the coordinator or foundation follow-up backlog 0.9e names.
- **2026-09-25, w2 inventory: an item from a listing needs the listing on the card at purchase time.** `addItem` with a `sourceListingId` checks the listing is in `app.v_listing_card` for this caller (so a user cannot record a purchase against a suppressed, unresolved or unknown listing ID), which also means adding from a listing fails while `listing-card` is off. Option taken: check at add time only; the row keeps the ID afterwards whatever happens to the listing. Conservative because it links only listings the user could actually see.
