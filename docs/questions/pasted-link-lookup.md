# Open questions: pasted-link-lookup

- **2026-09-25, w2 pasted-link-lookup: the per-user limit and whether it differs by tier.** The module card says the lookup is "rate-limited per user in the oRPC middleware (the limit is a starting value)" and that whether it is a metered "live on-demand lookup" is the owner's call (question 40). `docs/engineering.md` lists per-minute middleware limits for other endpoints but none for pasted links. Option taken: the module itself refuses a user's 21st distinct listing in a rolling 24 hours (`PASTED_LINK_LOOKUP_DAILY_LIMIT`, counted on server time from its own `requests` table), the same for every tier, and the oRPC middleware's per-minute limit (outside this module's files) is left for the web app task. Conservative because it bounds the paid fetches one account can cause well inside the free-tier daily bound (`docs/security.md`) without choosing a tier structure; the owner sets the real limits and any metering.
- **2026-09-25, w2 pasted-link-lookup: what a user is told.** The card says the module "tells the user when it is ready"; no wording is chosen. Option taken: the module exposes a status (`queued`, `ready`, `failed`) on `app.v_pasted_link_lookup_requests` and publishes `pasted-link-lookup.ready` (request IDs); the failure reason (`expired`, `fetch-failed`) stays in the table and is never shown. Any message text is the web app's and the owner's.
- **2026-09-25, w2 pasted-link-lookup: `shadow` refuses submits.** Rule 11 says `shadow` runs and writes but shows no user-facing rows. A pasted link is itself a user-facing action that can cost a paid fetch, so `submit()` requires `on`; `settle()` still runs in `shadow` so a test deployment can watch the tick. Conservative because nothing is spent for a user who cannot see the result; flagging in case the owner wants shadow submits recorded.
- **2026-09-25, w2 pasted-link-lookup: a suppressed listing may still cost one fetch.** `listing_suppression.v_suppressed` resolves suppressed listings by listing-ingest ID, so a listing the pipeline has never seen cannot be checked against the list before it is queued, and a known-but-unfetched listing is already in the details queue from its first sighting. Option taken: the settle tick sends the ID to the shared, deduplicated details queue as the card says, and the request never becomes `ready`, because `app.v_listing_card` leaves suppressed listings out; it closes as `expired` after the TTL. No user-facing output is ever produced for it. Flagging in case the owner wants the queue itself to refuse suppressed hashes (a details-queue change).
- **2026-09-25, w2 pasted-link-lookup: the card lookup scans `app.listing_card()`.** The module resolves a link to a listing through `app.v_listing_card where link = ...` (the card's named input), which computes listing-card's SECURITY DEFINER function over every visible listing per call, once per submit and once per settle tick. Correct and within rule 5, but not indexed. Option taken: accepted for the beta; recorded so the coordinator can weigh a `listing_known(source, source_listing_id)` SECURITY DEFINER predicate on listing-ingest (the shape `docs/security.md` already names) once the listing table is large.
