# Engineering conventions

Required reading for every task. These settle the questions an agent would otherwise have to guess.

## Toolchain

Node 22 LTS (`.nvmrc`), pnpm 10 (`packageManager` in `package.json`), TypeScript 5 strict, Next.js 16 App Router, React 19, Biome, Vitest, Playwright, Turborepo, Drizzle ORM and Drizzle Kit, Better Auth, oRPC, Trigger.dev v4 SDK, Vercel AI SDK, Zod 4. Pin exact versions in the lockfile; upgrade in a dedicated task.

## Packages and names

| Package | Path | Holds |
| --- | --- | --- |
| `@nabvy/contracts` | `packages/contracts` | Zod schemas and types for events, fact templates, pack format, oRPC input and output, model output contracts, enumerations |
| `@nabvy/db` | `packages/db` | Drizzle schema (one file per module), migrations, `withUser`, database roles, generated Better Auth schema, seed scripts. Row types come from Drizzle; `drizzle-zod` derives insert and select schemas so nothing is typed twice |
| `@nabvy/config` | `packages/config` | Zod-validated environment loading (`env.ts`), model price table, usage list prices, rate limits, caps. Every service imports config from here; nothing reads `process.env` directly |
| `@nabvy/packs` | `packages/packs` | Category packs as data |
| `@nabvy/<module>` | `services/<module>` | One per module in `docs/modules.md` |
| `apps/web` | `apps/web` | Next.js app: routes, oRPC router in `src/rpc/`, components, legal content in `content/legal/*.mdx` with `TODO-LEGAL` markers |
| `trigger/` | `trigger/` | Trigger.dev task files, thin |

Rule of two: an entity is defined once as a Drizzle table (source of persistence) and once as a contracts schema only if it crosses a boundary (event payload, API, model output). Do not hand-write a Zod schema that mirrors a table; derive it.

## Database access

- Roles: `nabvy_app` (web app; subject to RLS) and `nabvy_pipeline` (Trigger.dev tasks; subject to RLS with role-scoped policies). Neither has `bypassrls`. Migrations run as the Supabase `postgres` role from CI.
- `withUser(userId, fn)` in `@nabvy/db`: opens a transaction, runs `SET LOCAL app.user_id = <uuid>`, runs `fn(tx)`, commits. Policies on user tables: `USING (user_id = current_setting('app.user_id', true)::uuid)` for `nabvy_app`; pipeline policies grant `nabvy_pipeline` full access on pipeline-owned tables, read on `hunts` and `entitlements`, insert on `alerts` and `matches`.
- Pooled connections in transaction mode (Supabase pooler); never rely on session state outside a transaction.
- Every table has `created_at` and `updated_at` (trigger-maintained); soft delete only where the spec says so.
- Migrations: Drizzle Kit generates table changes; RLS policies, views, materialised views, partitions and pg_cron jobs are hand-written SQL migrations in the same folder, numbered in sequence. Forward-only.

## Identifiers and hashing

- IDs are UUID v7 generated by the database (`uuidv7()` function in a migration) so they sort by time.
- `cellId` is the H3 index at resolution 4 (Apache 2.0 `h3-js`), whose hexagons are about 45 km across; the UK grid is the set of resolution-4 cells covering Great Britain and Northern Ireland land area (about 100). `cell_provider_locations` maps a cell to each provider's location identifier (Facebook location ID, Gumtree area slug), filled by hand in task 1.0.
- `contentHash` = sha256 of `title|priceMinor|thumbnailUrl` after trimming and lowercasing the title.
- `sellerHash` = sha256 of `SELLER_HASH_SALT|source|sourceSellerId`.
- `photoFingerprint` = 16×16 blockhash (MIT `blockhash-core`) of the first photo resized with `sharp` (Apache 2.0); two photos match when Hamming distance ≤ 10.
- Image embeddings: `Xenova/clip-vit-base-patch32` through `@huggingface/transformers` in Trigger.dev tasks, 512 dimensions, cosine distance.

## Events and tasks

- Transport is Trigger.dev: an event `x.y` is a task with id `x-y` in `trigger/`, triggered with the envelope from `docs/contracts.md`; batch events pass arrays of IDs. Supabase Queues are the fallback transport and are not used unless Trigger.dev is unavailable.
- Scheduled tasks: `crawl-tick-60`, `crawl-tick-120`, `crawl-tick-300`, `crawl-tick-3600`, `recheck-tick` (every 10 minutes), `pricebook-nightly` (02:00 Europe/London), `pricebook-hourly`, `dashboards-refresh` (every 5 minutes), `retention-daily` (03:00), `usage-grants-daily` (00:10), `daily-brief` (07:30 Europe/London, sends at 08:00), `weekly-review` (Monday 07:30).
- Queues and concurrency: one Trigger.dev queue per provider with concurrency limits `facebook: 5`, `gumtree: 3`, `ebay: 10`, `cex: 1`, `models: 20`. Task idempotency keys are the envelope `key`.
- Retries: 3 attempts with exponential backoff (5 s, 30 s, 2 min); then the dead-letter table `incidents` with the payload and error.
- Scan mode on-demand fetch runs as a Trigger.dev task triggered from the oRPC procedure; the client subscribes to task progress through Trigger.dev Realtime to show each source completing; web functions never wait on providers.

## Errors, logging, config

- Domain functions return typed results (`{ ok: true, value } | { ok: false, error }`) for expected failures and throw only for bugs. Errors carry a stable `code` from a shared enum in contracts.
- Logging with `pino` (MIT), JSON, one logger per module with `module` and `taskId` fields; never log secrets, listing descriptions or personal data.
- `@nabvy/config` validates every environment variable at start-up with Zod and fails fast with the missing names.

## Cost metering

- Apify: after each run read `usageTotalUsd` from the run object; convert with `USD_GBP_RATE` (config, updated weekly) into `costMinor`.
- eBay and CeX: `costMinor = 0`, but calls are still counted against their daily limits.
- Models: `costMinor` from token usage × the model price table in config; Langfuse receives the same numbers.
- Every metered row goes to `provider_calls`; every user-facing metered action goes through `chargeUsage`.

## Storage

Supabase Storage buckets: `snapshots` (`<provider>/<yyyy-mm-dd>/<runId>.json.gz`, 30-day lifecycle), `scans` (`<userId>/<scanId>.jpg`, 30-day lifecycle unless referenced by `inventory_items`), `exports` (`<userId>/<exportId>.zip`, 7 days), `fixtures-export` (Review Console exports).

## Rate limits and abuse

Sign-up 5 per hour per IP; magic-link requests 5 per hour per email; scans 30 per minute per user; hunt writes 20 per minute per user; feedback 60 per minute per user; public API 600 requests per minute per key. Limits live in config and are enforced in the oRPC middleware with a Postgres-backed counter (no Redis).

## Admin bootstrap

`ADMIN_EMAILS` (config) lists founder addresses; on first sign-in an address in the list receives the `admin` role through the admin plugin, with an `audit_log` row.

## Local development

`supabase start` for a local Postgres with the same extensions; `pnpm db:migrate && pnpm db:seed` (seeds the founder user, the UK cells, the `gpu-pc` pack and fixture listings); `pnpm trigger:dev`; `pnpm dev:web`; Mailpit (MIT) catches magic-link emails; `stripe listen --forward-to localhost:3000/api/auth/stripe/webhook` for billing; Apify and eBay calls use recorded fixtures unless `LIVE_PROVIDERS=true`.

## Branches, pull requests, progress

- One branch per task: `task/<id>-<slug>`. One pull request per task with the definition of done as its checklist. CI must be green; a human merges.
- At the end of every task the agent updates `docs/progress.md` (status, date, PR link, notes) and the module `README.md`. A new session starts by reading `docs/progress.md`.
- Never rewrite history on `main`; never force-push.
